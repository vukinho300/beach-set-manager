# Shared Architecture

Status: `prototype_decision`

## Shared Petalon v1

Petalon is the only location required for the first shared release. Vuk, Vito and Mark use the same deployed application and the same authoritative Petalon data.

The minimal proposed backend shape is:

- `locations` — location identity/configuration;
- `location_memberships` — links authenticated users to Petalon, includes `active` and a role field for future differentiation;
- `location_state` — one current versioned JSONB application-state record for Petalon.

This intentionally mirrors the existing `AppData` model instead of normalizing every set, reservation, transaction and Aquapark concept before shared operation has been proven.

## State authority

Once migration is enabled for Shared Petalon v1, the Supabase `location_state` row is authoritative for shared operational state. Browser `localStorage` is no longer the cross-device source of truth.

The state record must include a monotonically increasing revision/version. Writes are accepted only against the expected current revision so two users cannot silently overwrite each other's newer state.

If a stale write loses the revision race, the client reloads authoritative state and reports a conflict/retry rather than silently using last-write-wins.

## Access boundary

Every exposed table has RLS enabled.

A normal application user may read/write Petalon state only while an active `location_memberships` row links `auth.uid()` to Petalon. Role-based differences can be added later; active membership is the first shared-release authorization requirement.

Vuk retains platform/developer authority outside the public browser client. No service-role/secret credential is shipped to the frontend.

## Realtime

After a successful initial load, clients should subscribe to Petalon state changes or use an equivalent invalidation/reload mechanism. The first implementation should prefer correctness and simplicity over a complex event-sourcing system.

## Deferred architecture

Do not implement session-seat/device limits, offline mutation queues, multi-location provisioning automation, white-labeling or seasonal licensing as part of Shared Petalon v1.

When a second real location is required, revisit whether the shared-state JSONB approach is still sufficient and design the provisioning pipeline from evidence gathered from Petalon.
